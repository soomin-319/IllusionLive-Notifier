# 댓글 알림 설계

작성일: 2026-09-12
대상: `IllusionLiveNotifier.Android`

## 목표

지금 앱은 `illusionlive.com` RSS로 **새 게시글**만 알린다. 여기에 **댓글 알림**을 더한다.

- 내가 쓴 글에 다른 사람이 댓글을 달면 알린다
- 내가 쓴 댓글에 다른 사람이 답하면 알린다

## 사이트 조사 결과

illusionlive.com은 아임웹(Imweb) 기반이다. 글 URL이 `?bmode=view&idx=<숫자>` 형태이고 이미지가 `cdn.imweb.me`에서 온다.

### 댓글은 비로그인으로 읽힌다

쿠키도 CSRF 토큰도 없이 200을 준다.

```
POST https://www.illusionlive.com/ajax/post_comment_paging.cm
     board_code=<b…>&post_code=<p…>&current_page=1
  → {"msg":"SUCCESS","html":"<div class=\"comment\" id=\"c2026091113d196d291259\">…"}
```

응답 HTML에서 뽑히는 값:

| 값 | 예시 | 쓰임 |
|---|---|---|
| 댓글 코드 | `c2026091113d196d291259` | 새 댓글 판별 (앞 8자리가 작성 날짜) |
| 작성자 닉네임 | `유메루` | 내 것인지 대조 |
| 회원 코드 | `m20251001affab7b73c402` | (현재 미사용) |
| 본문 | `이거 맞아염` | 알림 문구 |

댓글 **쓰기**만 로그인이 필요하다(`SITE_MEMBER.openLogin`). 읽기는 전부 열려 있다. 따라서 **앱에 로그인 기능을 넣지 않는다.**

### 필요한 파라미터는 글 페이지에서 한 번만 얻는다

`post_comment_paging.cm`은 `board_code` + `post_code` + `current_page` 세 개를 모두 요구한다. RSS가 주는 `idx`로는 동작하지 않는다(측정: `idx`만 / `post_code`만 / `board_code`+`post_code` 모두 `"댓글 조회에 실패했습니다"`).

두 코드는 글 페이지 HTML의 hidden input에 있다.

```html
<input type="hidden" name="post_code"  value="p20260809213e43a4f8ac7">
<input type="hidden" name="board_code" value="b20260808bcd2709bb86e5">
```

글마다 고정값이므로 **글당 1회만** 받고 저장한다. 이후 재확인은 댓글 API만 호출한다.

| 요청 | 크기(gzip) | 시간 | 빈도 |
|---|---|---|---|
| 글 페이지 (코드 추출) | 61 KB | 0.39 s | 글당 1회 |
| 댓글 목록 | 7 KB | 0.25 s | 재확인마다 |

### 댓글은 평면 구조다 — 스레딩이 없다

이 사이트에는 "댓글의 댓글"이 데이터로 존재하지 않는다.

- 댓글 달린 글 85개 이상을 확인했고 중첩된 댓글은 0건
- 모든 댓글이 `main_comment` 클래스를 달고 부모 참조가 없다
- `post_comment.js`가 부르는 `POST /ajax/getChildComment.cm`은 이 사이트에서 404 (철자 4종 모두)
- `_comment_at_nick` 스팬은 멘션이 아니라 **작성 시각** 필드다

사람이 "대댓글"이라 부르는 것은 같은 글에 달린 또 다른 평면 댓글이다. 실제 예(`/134/?idx=172966140`):

```
1 위즐리어카   밑에 영상 링크가 잘못된 것 같아염   2026-08-09 01:32
2 유메루       이거 맞아염                      2026-08-09 01:35   ← 1에 대한 답
3 현랑화       앞으로도 즐겁고 행복한 활동 하길!   2026-08-09 01:39
4 유메루       앞으로도 잘 부탁해!!              2026-08-09 01:45   ← 3에 대한 답
```

2번과 4번은 답변이지만 저장 구조상 1·3번과 완전히 대등하다. **누가 누구에게 답했는지 사이트가 기록하지 않는다.** 앱은 순서로 추정할 수밖에 없다.

### 댓글은 이틀 안에 멈춘다

RSS 글 24개(댓글 43개)의 "글 게시일 대비 댓글 작성일" 분포:

```
D+0   24건   누적  55.8%
D+1   11건   누적  81.4%
D+2    8건   누적 100.0%
D+3 이상  0건
```

RSS 창이 4.6일치라 D+5 이상은 관측되지 않았으나, 관측 가능한 D+3·D+4 구간도 0건이다. **추적 보관 기간을 3일로 정한 근거.**

### 새 글 유입

RSS 50개가 111.5시간 분량 → 약 **10.8개/일**.

## 범위

포함:

- 내가 쓴 글의 새 댓글 알림
- 내가 쓴 댓글에 달린 답 알림
- 첫 실행 안내에서 닉네임 입력, 건너뛰면 두 기능 모두 꺼짐
- 설정에서 두 기능 개별 on/off, 닉네임 변경

제외:

- 앱 내 로그인 — 읽기에 필요 없고, 자체 서명 APK에 계정 자격증명을 두지 않는다
- RSS 창(약 50개, 4.6일) 밖 옛날 글 — 사용자가 명시적으로 포기하기로 함
- 회원 코드 기반 신원 — RSS `<author>`가 닉네임만 주므로 어차피 닉네임이 기준이 된다

## 설계

### 신원

`nickname` 문자열 하나. 빈 값이면 댓글 관련 네트워크 요청이 **0건**이다.

- 저장 시 두 스위치를 자동으로 켠다
- 대조는 앞뒤 공백을 제거한 **정확한 문자열 일치**. 동명이인은 구분하지 않는다
- 닉네임을 바꾸면 `tracked_posts`·`seen_comment_ids`·`scanned_posts`·`comments_initialized`를 모두 지운다. 남겨 두면 이전 닉네임 기준으로 모은 추적 대상에서 엉뚱한 알림이 나간다

입력 시 검증: 캐시된 글 작성자와 이미 받아 둔 댓글 작성자 중에 그 닉네임이 있는지 본다. 없으면 "최근 글에서 이 닉네임을 찾지 못했습니다. 그대로 저장할까요?"로 확인한 뒤 저장한다. 추가 네트워크 요청은 없다. 오타 때문에 알림이 영영 오지 않는 사고를 막는 용도이며, 저장을 막지는 않는다.

### 저장 상태

기존 `settings` SharedPreferences에 추가한다.

| 키 | 형태 | 설명 |
|---|---|---|
| `nickname` | String | 빈 값 = 기능 전체 off |
| `comment_my_posts` | bool | 스위치 1 |
| `comment_my_replies` | bool | 스위치 2 |
| `tracked_posts` | String | 레코드 구분자 인코딩. 상한 20개, 3일 만료 |
| `seen_comment_ids` | StringSet | 상한 500 (기존 `seen_ids`와 같은 방식) |
| `scanned_posts` | StringSet | 상한 200. 발견 스캔 재실행 방지 |
| `comments_initialized` | bool | 첫 시딩 완료 여부 |

`tracked_posts` 한 줄: `url ⟂ post_code ⟂ board_code ⟂ 등록시각 ⟂ 사유(MY_POST|MY_COMMENT) ⟂ 마지막확인시각`

`FeedParser`가 쓰는 `0x1f`/`0x1e` 구분자 방식을 그대로 쓴다. 코드 값은 `[0-9a-f]`와 접두 문자만 허용하므로 구분자가 섞일 수 없다.

### 흐름

기존 5분 알람 사이클에서 RSS 처리가 끝난 뒤 이어서 돈다.

```
RSS 처리 (기존 그대로)
 │
 ├ 내 글 감지  (스위치1 ON일 때만)
 │    post.author == nickname 이고 아직 추적에 없는 글
 │      → 글 페이지 61KB → post_code / board_code
 │      → 추적 등록 (MY_POST)
 │
 ├ 발견 스캔  (스위치2 ON일 때만, 사이클당 최대 3글)
 │    scanned_posts에 없고 내 글도 아닌 RSS 글
 │      → 글 페이지 61KB → post_code / board_code
 │      → 댓글 7KB → 내 닉네임의 댓글이 있나?
 │           있으면 추적 등록 (MY_COMMENT)
 │      → scanned_posts에 기록 (있든 없든)
 │
 └ 추적 재확인  (사이클당 최대 8글, 오래 확인 안 한 것 우선)
      댓글 목록 7KB → seen_comment_ids에 없는 코드 = 새 댓글
        내가 쓴 댓글은 제외
        알림 규칙(아래) 적용
        seen_comment_ids 갱신
```

새 댓글 판별은 **댓글 코드로만** 한다. 시각은 쓰지 않는다 — 최근 댓글은 `17시간 전`, 오래된 댓글은 `2026-09-03 14:14`로 형식이 갈려 신뢰할 수 없다.

### 알림 규칙

| 스위치 | 대상 글 | 알리는 댓글 |
|---|---|---|
| 내 글에 달린 댓글 | 사유 `MY_POST` | 그 글의 **새 댓글 전부** |
| 내 댓글에 달린 답 | 사유 `MY_COMMENT` | 내 댓글 **바로 다음 댓글 1건** |

스위치2가 "바로 다음 1건"인 이유: 평면 구조라 답변 대상을 데이터로 알 수 없고, 순서가 유일한 단서다. 글당 댓글이 평균 1.8개(글 24개 / 댓글 43개)라 사이에 제3자가 끼어들 여지가 작다.

알려진 오차:

- 내 댓글과 답 사이에 제3자 댓글이 끼면 **놓친다**
- 내 댓글이 마지막일 때 무관한 새 댓글이 달리면 **헛알림 1건**

한 글이 두 사유에 모두 해당하면(내 글에 내가 댓글도 단 경우) 같은 댓글을 두 번 알리지 않는다.

### 비용

추적 재확인을 **사이클당 8글로 제한**한다. 추적 글이 더 많으면 오래 확인하지 않은 것부터 라운드로빈으로 돈다. 추적 수와 무관하게 최악치가 고정된다. 발견 스캔(사이클당 3글)과 내 글 등록은 이 상한과 별개이며, 둘 다 글마다 한 번만 일어나므로 누적되지 않는다.

```
재확인   상한 8 × 7 KB × 288 사이클 = 16 MB/일   (화면 켠 채 하루 종일 쓴 최악치)
발견 스캔          10.8글/일 × 68 KB ≈ 750 KB/일
내 글 등록         내가 쓴 글 수 × 61 KB
```

Doze가 걸리면 알람이 9분에 한 번꼴로 늘어지므로 실제 값은 이보다 낮다. 보관 3일 기준 추적 글은 보통 10개 남짓이고, 한 바퀴 도는 데 2사이클(약 10분)이다.

### UI

**첫 실행 안내** — 6번째 페이지를 추가한다. 제목 "댓글 알림 받기", 닉네임 입력칸, `건너뛰기` 버튼. 건너뛰면 닉네임이 빈 값으로 남아 두 기능이 꺼진 채 시작한다.

**설정** — 게시판 목록 위에 카드 하나를 넣는다.

```
닉네임                        유메루  ›
내 글에 달린 댓글                  [●─]
내 댓글에 달린 답                  [●─]
```

닉네임 행을 누르면 입력 다이얼로그가 열린다. 처음 저장하면 두 스위치가 켜진다. 닉네임이 비어 있으면 스위치는 꺼진 채 비활성으로 보인다.

**알림 채널** — `new_comments`를 새로 만든다. 기존 `new_posts`와 분리해 OS 설정에서 따로 끌 수 있게 한다. 알림을 누르면 해당 글 원문이 열린다. 여러 건이면 기존 `notifyPosts`처럼 `InboxStyle`로 묶는다.

### 첫 시딩

닉네임을 처음 저장하면 `comments_initialized = false`가 된다. 다음 사이클에서 찾은 댓글은 전부 `seen_comment_ids`에 넣고 알리지 않는다. 기존 "첫 실행 시점의 글은 기준으로만 저장한다" 규칙과 같다.

### 파일

| 파일 | 상태 | 역할 |
|---|---|---|
| `CommentChecker.java` | 신규 | 발견 스캔, 추적 재확인, 알림, 추적 목록 관리 |
| `CommentParser.java` | 신규 | 댓글 HTML → (코드, 닉네임, 회원코드, 본문) 목록. 글 페이지 → `post_code`/`board_code` |
| `Tutorial.java` | 신규 | `MainActivity`에서 첫 실행 안내를 분리 |
| `FeedChecker.java` | 수정 | RSS 처리 뒤 `CommentChecker` 호출 |
| `MainActivity.java` | 수정 | 설정 카드, 닉네임 다이얼로그. 안내는 `Tutorial`로 이동 |
| `SelfTest.java` | 수정 | 아래 항목 추가 |

`MainActivity`는 이미 1109줄이고 이번에 설정 카드와 다이얼로그가 더 붙는다. 어차피 안내 화면을 수정하는 김에 `maybeShowTutorial`과 `TUTORIAL` 배열(약 110줄)을 `Tutorial.java`로 옮긴다. 이번 작업이 건드리는 범위 안이다.

### 파싱과 보안

댓글 HTML은 신뢰할 수 없는 입력이다. `FeedParser`가 이미 쓰는 방어를 그대로 따른다.

- 응답 크기 상한을 둔다(`FeedChecker.readLimited`와 같은 방식)
- 코드 값은 `^[cpbm][0-9a-f]{1,40}$`를 통과한 것만 저장한다. 저장 형식의 구분자가 섞이는 경로를 막는다
- 알림에 넣는 닉네임·본문은 제어문자를 지우고 길이를 자른다(`FeedParser.clean`과 같은 방식)
- 여는 URL은 기존 캐시에 저장된 `https://www.illusionlive.com/…` 링크만 쓴다. 댓글 HTML에서 URL을 꺼내 쓰지 않는다

중첩 댓글 대비: 파서는 `<div class="comment">`를 중첩까지 전부 수집한다. 언젠가 스레딩이 켜져도 "그 글의 새 댓글"로 잡혀 알림은 나간다. 확인하지 못한 마크업을 추측해서 구현하지 않는다.

### 테스트

실제 응답을 픽스처로 박아 `SelfTest`에 넣는다.

- 댓글 6개짜리 응답에서 코드·닉네임·본문이 순서대로 나오는지
- 글 페이지에서 `post_code`/`board_code`를 뽑는지
- 내가 쓴 댓글은 알림 대상에서 빠지는지
- 스위치2가 내 댓글 **바로 다음 1건**만 고르는지 (앞·뒤 댓글은 제외)
- 두 사유에 모두 걸린 글에서 같은 댓글이 두 번 알림 대상이 되지 않는지
- 첫 시딩에서는 아무것도 알리지 않는지
- 추적 상한 20·3일 만료·사이클당 8회 상한이 지켜지는지
- 닉네임 변경 시 관련 상태가 모두 지워지는지
- 형식에 맞지 않는 코드가 저장되지 않는지

### 버전

기능 추가이므로 마이너를 올린다. `build-android.ps1`: `--version-code 13 → 14`, `--version-name 1.0.12 → 1.1.0`.

## 알려진 한계

이 문서의 설계로 해결되지 않는 것들이다.

- **RSS 창 밖의 글** — 약 50개, 4.6일치를 넘어간 글에 달리는 댓글은 감지하지 않는다. 댓글의 100%가 D+2 안에 달리므로 실제 손실은 거의 없다
- **동명이인** — 닉네임이 같은 사람의 글과 댓글을 내 것으로 본다
- **답변 대상 추정** — 스위치2는 순서 기반 추정이다. 위의 "알려진 오차" 참고
- **비공개·회원 전용 글** — RSS에 노출되지 않으므로 지금도 감지하지 못한다. 변화 없음

## 구현하며 바뀐 점

구현 중에 위 설계와 달라진 부분이다. 둘이 다르면 코드와 이 절이 맞다.

- **첫 시딩은 글마다 한다.** `comments_initialized` 는 없다. 추적 글의 마지막 확인 시각이 0이면 그 글의 첫 확인이라, 댓글을 전부 `seen_comment_ids` 에 넣고 알리지 않는다. 전역 플래그로는 첫 사이클 뒤에 추적을 시작한 글의 기존 댓글이 한꺼번에 알림으로 나간다.
- **내 글 등록도 사이클당 3글까지이고, 한 번 연 글은 `scanned_posts` 로 기억한다.** 기억하지 않으면 추적 상한 20에 밀려난 내 글을 사이클마다 다시 받는다(사이클당 상한까지 없으면 내 글 30개일 때 하루 약 170 MB). 내 글 등록과 발견 스캔 모두 게시한 지 3일이 지난 글은 글 페이지를 받지 않고 건너뛴다. 페이지를 받은 글은 코드가 없어도 `scanned_posts` 에 남긴다. 받기에 실패했거나 시간이 다 돼 댓글을 못 본 글만 다음 사이클에 다시 시도한다. 발견 스캔은 위 흐름대로 내 글을 건너뛴다 — 발견 스캔이 먼저 연 내 글은 내 글 등록이 영영 건너뛰기 때문이다.
- **`scanned_posts` 와 `seen_comment_ids` 는 개수 상한 대신 남길 기준으로 자른다.** `scanned_posts` 는 캐시에 남아 있고 게시 3일이 안 된 글만 남긴다. `seen_comment_ids` 는 날짜가 가장 최근인 코드 500개를 남긴다 — 댓글 코드는 `c` 뒤 여덟 자리가 작성 날짜라 문자열 역순이 최신순이다. 기존 `seen_ids` 방식(이번 사이클 것을 먼저 채우고 나머지는 해시 순서)으로 자르면, 몇 주 뒤부터 창 안의 글이 밀려나 글 페이지를 사이클마다 다시 받고 추적 중인 글의 댓글 코드가 밀려나 같은 댓글을 다시 알린다.
- **댓글 확인에 시간 예산을 둔다.** 사이클 시작(RSS 포함) 후 10초가 지나면 새 요청을 시작하지 않고 모은 것까지만 저장한다. 댓글 요청의 제한 시간은 연결 5초, 읽기 8초라 늦어도 약 23초 안에 끝난다. 당겨서 새로고침은 목록을 먼저 보여 준 뒤 댓글을 확인한다. 알람은 댓글 확인까지 마치고 끝난다. 댓글 확인 중에 새로고침하면 저장된 목록을 다시 보여 준다.
- **사이클 도중 닉네임이 바뀌면 그 사이클은 아무것도 저장하지 않고 알리지도 않는다.** 저장과 닉네임 변경이 같은 잠금을 쓴다.
- **닉네임 검증은 캐시된 글 작성자만 본다.** 댓글 작성자는 저장하지 않는다. 첫 실행 안내의 `시작하기` 와 설정 다이얼로그가 같은 확인을 쓴다. 안내의 `건너뛰기` 는 입력칸에 무엇을 적었든 닉네임을 저장하지 않는다.
- **스위치2는 나중에 단 내 댓글도 찾는다.** 발견 스캔은 글마다 한 번뿐이라, 원래 설계로는 그 뒤에 단 댓글을 찾지 못한다. 발견 스캔에서 댓글 목록을 받은 글을 `comment_candidates` 에 후보로 남긴다. 후보는 게시 시각 기준 최신 20개이고 게시 후 3일에 만료된다. 스위치2가 켜져 있으면 추적 재확인 뒤에 후보를 사이클당 2글씩 댓글 목록만 다시 받는다. 내 댓글이 보이면 `MY_COMMENT` 로 추적하고 시딩하지 않으므로, 그 사이 달린 답을 바로 알린다. 스위치2를 껐다 켜면 꺼져 있던 동안 달린 답도 한 번 알린다. 추적으로 옮긴 글은 후보에서 빠지므로, 추적 상한에 밀려나면 다시 찾지 않는다. 닉네임을 바꾸면 후보도 지운다.
- **비용.** 재스캔이 2 × 7 KB × 288 사이클 ≈ 4 MB/일을 더한다. 화면을 켠 채 하루 종일 쓴 최악치는 16 MB/일에서 약 20 MB/일이 된다.
- **댓글 목록은 첫 페이지만 읽는다.** 한 페이지에 몇 개까지 오는지는 재지 못했다(댓글 18개인 글은 한 페이지에 다 왔다). 첫 페이지를 넘길 만큼 댓글이 달린 글에서는 새 댓글을 놓칠 수 있다.
